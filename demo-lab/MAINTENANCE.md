# PM-01 local maintenance desk

This is an executable synthetic vertical slice for PM-01 Property Management, which remains **PARTIAL**. It implements intake, a bounded deterministic emergency hold, occupant-owned access grants, lease/skill/window planning, independent hash review, local reservations and dispatch evidence, reconciliation, cancellation and operator-reported completion. It does not run a property business or contact a tenant, vendor, emergency service or property platform.

## Reproduce

Use Node 24 with built-in `node:sqlite` from the repository root:

```sh
node --test demo-lab/maintenance-core.test.mjs
node demo-lab/run-maintenance.mjs
```

The test suite exercises 44 cases, including two real independent processes competing for one appointment, a separate process reopening an uncertain dispatch, SQL-trigger rollback, consent and lease/window boundaries, tenant/role selectors, independent review, immutable replay, and durable corruption checks. Its single receiver/booking/outbox are actual rows in that local SQLite database. No provider acceptance or physical service is implied.

## Clock and fixtures

The default trusted clock is deliberately fixed at **2026-10-24T12:00:00.000Z**. The catalog labels this fixed synthetic scenario clock. Access/vendor appointments are on that synthetic date; browser examples remain reproducible on later days because this clock never follows wall time. SLA readouts are elapsed minutes from caller-provided synthetic `receivedAt` to this clock, with a 5-minute emergency / 1440-minute routine target. They are not active monitoring or a provider SLA. An internally injected `clock` factory option supports boundary tests; HTTP callers cannot choose a clock.

Two fixture tenants, `acme` and `beta`, have separate active leases, occupants, operators, reviewers and vendors. Plumbing vendors are available 13:00â€“18:00Z and electrical vendors 15:00â€“18:00Z. Example occupant access is 13:00â€“16:00Z. Actor and tenant labels are **unauthenticated fixture selectors**, not an authorization system. Server-held registries determine the permitted roles, occupant ownership, lease dates, vendor approval, skills and availability; callers cannot supply approval booleans or vendor URLs. Dual-role fixture labels exist to demonstrate self-review rejection.

## Lifecycle and invariants

1. Intake requires an immutable `commandId`, tenant-scoped `sourceIssueId`, configured lease and operator, description, structured hazards, skill, duration and canonical UTC `receivedAt`. All fields are closed, bounded JSON; unknown fields, unsupported prototype data, control characters, non-finite values, invalid UTC dates and future received timestamps fail before an event.
2. Any configured structured hazard (`gas`, `fire`, `flood`, `electrical-danger`, `carbon-monoxide`, `unknown-danger`) or a known text trigger (`gas leak`, `smell of gas`, `fire`, `smoke`, `sparks`, `flooding`, `carbon monoxide`, `exposed wires`) causes `emergency-hold`. Text triggers are case-insensitive with word boundaries and whitespace between phrase words. This is a documented fixture classifier, **not complete hazard detection or emergency response**. Review cannot downgrade a hold. Emergency cases can be locally cancelled with a mandatory follow-up indication; routine dispatch remains forbidden.
3. A routine case starts `access-required`. Only the configured lease occupant selector grants sorted, disjoint, canonical UTC access windows inside the lease. Grant replacement or revocation increments access revision and invalidates the entire proposal/review. A pre-send grant change releases a queued local reservation. Revocation is allowed after dispatch: it preserves receiver evidence, marks `access-revoked` / `requiresFollowUp` and blocks further dispatch. Post-send capacity remains reserved until explicit local cancellation, so revocation cannot create two overlapping received appointments. Uncertain delivery must first reconcile before that cancellation. This does not recall a real vendor.
4. Planning intersects the active lease, current clock, live access, eligible vendor skill/approval and vendor availability. It skips active reservations across cases, uses half-open intervals (adjacent appointments are allowed), and selects earliest time then vendor identifier. A proposal records its proposing actor. Its hash binds original issue data, lease, vendor, exact slot, proposing actor, access revision/windows and source/config hashes.
5. Independent review must differ from both intake and proposal actors and bind the current proposal hash. Rejecting review prevents dispatch. New access or a new proposal clears prior review.
6. Dispatch rechecks all authority inside `BEGIN IMMEDIATE`, including current lease/access/skill/windows, source/config identity, approved hash and cross-case reservation conflicts. A newly occupied slot rejects the old reviewed proposal; propose and review again. Offline attempts reserve one local slot and keep one pending outbox row. Retrying with a new command increments attempts without multiplying reservations.
7. `online` creates one local receiver row and acknowledges it. `lose-response` commits the same real local receiver effect but exposes `uncertain` with an uncertain outbox and no known receipt identifier. A new send or cancellation is forbidden until `reconcile` inspects that actual receiver and matches its sent proposal hash. Exact replay of the original command returns current case state without another effect. Reconciliation does not resend. Access revocation remains permitted while uncertain; later reconciliation acknowledges the outbox but retains the access-revoked warning and active capacity hold. Explicit cancellation is required to release that hold and cancel the local receiver record together.
8. Local cancellation requires the current revision, releases the reservation and preserves a cancelled local receiver row if one existed. Completion requires current revision and a reconciled delivered case; it records **operator-reported completion, not proof of a physical visit**. Completion can be reported in the fixed scenario without waiting until the appointment. Terminal cases do not dispatch again.

A `commandId` is unique across all operations within one tenant. Reusing it with a different operation or payload conflicts. Exact replay returns the **current receipt**, not a frozen historical response. A new command for an existing `sourceIssueId` conflicts; replay its original intake command to recover that case. Receipt revisions and hash-bound review protect different transitions: `cancel` and `complete` require `expectedRevision`; review requires `expectedHash`. Grant/propose/dispatch/reconcile have closed schemas without those extra fields.

## API surface

`maintenanceDesk(DatabaseSync, options?)` uses a caller-owned database; `openMaintenance(path, options?)` owns/opens it and adds `close()`. Initialization sets a five-second busy timeout before opening schema transactions. Open failures close the owned handle. Options accept only an internal `clock` and bounded `registryRevision` identity. Changing source bytes or configuration revision makes existing authority stale; this slice intentionally has no migration/reapproval workflow.

The desk provides `catalog`, `intake`, `grantAccess`, `revokeAccess`, `propose`, `review`, `dispatch`, `reconcile`, `cancel`, `complete`, `receipt`, `history`, `state`, `audit` and `verifyAudit`. `catalog()` returns scenario inputs, fixture role selectors, lease/vendor registries, clock and the three closed receiver profiles. Other methods use tenant/case selectors; no caller-selected transport address or external integration is accepted. `state({tenant})` exposes that tenant's cases, bookings, outbox and receiver rows. Reads run in a consistent SQLite transaction and return copies.

The integration routes live in the demo server and browser desk; their authentication boundary remains the same explicitly local fixture boundary. The complete method payload examples are exercised directly in `maintenance-core.test.mjs` and `run-maintenance.mjs`.

## Durable evidence and limits

Each successful command, next case revision and row effect is recorded in a hash-linked event. A separate durable singleton anchors event count and head hash. Every mutation verifies the complete chain, replay-derived case revisions, anchor and actual booking/outbox/receiver row bytes before and after writing. Changes to recorded request bytes, an event tail, head, receiver or booking fail closed. The owned opener also rejects a missing head on restart instead of reinitializing it. Source identity hashes the exact bytes of both core and fixture modules; configuration identity covers the registry and revision.

Reservation/outbox/receiver updates, event append and head update commit or roll back together in a **single SQLite database**. These are local atomic effects, not distributed exactly-once delivery. The hash chain is unkeyed; a privileged administrator who coherently rewrites all events, rows and anchors is outside its guarantee. There is no signed identity, authenticated review, production privacy certification, real vendor acceptance, recorded physical visit, provider outage recovery or actual emergency escalation. Existing PM blueprint requirements for integrated rent/lease operations, property-platform adapters, reconciliation/rollups, real communication approvals and acceptance evidence remain open.
